# Custom Golf Stats v1: Build Roadmap

**Spec:** `docs/superpowers/specs/2026-11-10-custom-golf-stats-v1-design.md`
**Legacy reference:** `docs/reference/golftrack/` (copies of golftrack's schema, views and stored procedures; the source of truth for stat definitions)

The spec covers six subsystems. Each phase below gets its own detailed plan (`docs/superpowers/plans/YYYY-MM-DD-phase-N-<name>.md`), written when the phase before it is merged, so it can use the real names and signatures that phase produced. Each phase ends with working, tested software.

Phases 4 and 5 can run in parallel once phase 2 is merged.

**Carried over from phase 1 (done 2026-11-11, 117 tests):**
- Phase 2: add `Directory.Packages.props` when the API brings packages. Stats tables should take course/tee names from the current entity, not from the first round. Validate quick-entry holes with `HoleSummaryValidator` and shot holes with `ShotValidator` at the API boundary. Add the handicap tile/history from handicap entries.
- Phase 3: check whether legacy `Putts = 0` sometimes means "not entered" (it would inflate hole-out %). Expect intended parity differences from these phase 1 decisions: eagles include albatrosses; driving and GIR-from-fairway/left/right ignore par 3 flags; birdie conversion counts only GIR birdies; sand saves count greenside sand only; the 18-hole histogram has 4 buckets (<80, 80–89, 90–99, 100+).
- Dropped from golftrack on purpose: short/long tee-miss tendencies and the blended to-par-by-tee-result averages (the spec lists only left and right).

**Branding (phases 4, 5, 7):** all logos, colors and icons come from Ron's brand kit, `docs/custom-golf-stats-brand.zip`. Its `BRAND.md` defines colors and usage. It includes SVG/PNG logo lockups and marks, web favicons, a manifest, an OG image and a head snippet, plus Android launcher icons and `brand_colors.xml`. The phase 4 and 5 plans start by unpacking it to `brand/` and deriving the web CSS tokens and Uno theme resources from `BRAND.md`. Never invent colors or logos.

**Carried over from phase 2 (done 2026-11-12, 347 tests, PR #1):**
- Decisions made during the build: weather comes from Open-Meteo (a commercial plan is needed before paid launch). The sync cursor is `nextSince`, which is server time minus a 2-minute margin, so clients must expect duplicates. Deleted rounds can't be revived. A trial round is used when a round first becomes shot-by-shot. External sign-in links to an existing account only when both emails are confirmed, so password accounts can't add Apple/Google until email confirmation exists. Tokens of a disabled account stay valid for up to 1 hour. Imported tees with no rating or slope are stored as 0/113 for an admin to fix. Admin corrections and course merges re-derive shot-by-shot rounds; quick rounds keep what the golfer entered. Handicap entries come over in full on every sync.
- Phase 3 (migration tool): write rounds directly rather than through `RoundUpsertService` (it counts trials and calls weather). Set `TrialCounted` for migrated shot rounds. Respect the unique `normalized_email` index and the shot -> (hole result, round) composite key.
- Phase 4/5 client contract: send `nextSince` back as `since`, URL-encoded. `PUT /me` replaces the whole profile. A push without weather keeps the stored weather, so a device can't clear it. Create courses and tees with client-generated ids so retries are safe. Scorecard rows are in play order, followed by unplayed holes. The generated client lives in `src/CustomGolfStats.Api.Client` and is regenerated by the API build.
- Phase 6 (deploy): migrations only run automatically in Development, so add a migration step. Set a fixed data-protection application name, and consider encrypting the keys stored in the database. Pin the SDK in `global.json`: local 10.0.0 and CI 10.0.x once produced different OpenAPI output.
- Deferred minors worth doing later: a lock between the "version in use" or "played holes" checks and their saves (admin-only, narrow race); `POST /courses/{id}/tees` should reject merged courses; some 409/502 problem responses are missing from the OpenAPI document; course flags don't follow merges; the first-time settings PUT race; `LoadAsync` loads every round per stats call.

**Carried over from phase 3 (done 2026-11-12; runbook `docs/migration/README.md`):**
- Real run on Ron's backup, into a local database only: 1,629 rounds, 24,681 holes, 678 handicap entries, 115 courses and 153 tees, in about 6 seconds. The parity check gave 6,011 matches, 245 intended differences, 0 unexplained and 1,117 not compared.
- Findings from the real data:
  - About 1,200 active rounds sit on tees or courses that golftrack marks inactive, so every played tee is imported.
  - 1,084 durations are stored as "H:MMh".
  - Three March 2022 rounds were moved to the tee their holes belong to ("Course #1 - 2020" instead of "- 2022").
  - Duplicate rounds on 14 days, all imported and listed.
  - 3 tees have no rating or slope, so they were imported as 0/113 and need admin fixes.
  - Every hole with 0 putts and a score above 1 looks like a hole-out, judged by its GIR flag. So `Putts = 0` does not mean "not entered".
  - golftrack's `Round_SeasonSummary` counts hole rows rather than rounds and always returns 0 for the 9/18 split. Treat it as a golftrack defect.
- The ShotScope tables (`SS_*`, 26 rounds with shots) are in the backup but not migrated. They are a possible source of shot-by-shot data later.
- Before production: import before any device syncs, since re-runs hard-delete imported rounds and send no tombstones. Apply migrations to the target first. golftrack tees that were really versions of one tee (e.g. "Course #1 - 2020/2022") could be merged into tee versions with the admin tools.

**Carried over from phases 4 and 5 (2026-11-12/13):**
- Web (phase 4) is done: Astro 7 SSR, encrypted session cookie, every stats section, scorecards, courses, profile, admin, CI. It was checked locally against the real API with the imported golftrack data. Deploy needs `API_BASE_URL`, `SESSION_SECRET` (runtime) and `ALLOWED_HOSTS` (build time).
- App core (phase 5 tasks 1–3) is done: SQLite store (schema v2 with shot drafts), sync engine, view models.
- **Before the app ships, phase 5 task 4 must first:**
  - write the account-switch marker before persisting new tokens (or sign out on any failure after sign-in), so one account's unsynced rounds can't sync into another;
  - catch a superseded course search's network errors;
  - make pull storage per-item isolated;
  - count shot drafts in the account-switch check;
  - guard decimal overflow for huge ratings;
  - clear drafts when a hole is deleted from the round list;
  - install a global unhandled-exception handler.
- Decisions:
  - Plus handicaps are shown as "+x.x".
  - 3-putt avoidance is 1 − the three-putt rate.
  - The app accepts 1–18 holes for a manual course, the API's rule.
  - Course limits now live in `Domain/Courses/CourseLimits`.
