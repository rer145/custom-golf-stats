# Phase 4: Astro Web Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The full-screen Custom Golf Stats web site (spec §3.5): sign in, every golftrack stats section, round history and scorecards, course search/import/manual entry, profile and handicap, and the `/admin` area. Everything except the landing and auth pages is behind a login.

**Architecture:** Astro 5, server-rendered with the Node adapter (`output: 'server'`), TypeScript strict, in `web/`. Pages call the API **from the server only**. Typed API access comes from the committed OpenAPI document (`src/CustomGolfStats.Api.Client/openapi/CustomGolfStats.Api.json`) via `openapi-typescript` (generated types, committed, regenerated by an npm script) and `openapi-fetch`. Auth tokens from `/auth/login` live in an AES-GCM encrypted, httpOnly, Secure, SameSite=Lax cookie (key from `SESSION_SECRET`); middleware refreshes the access token with `/auth/refresh` when it's near expiry and redirects to `/sign-in` when there's no session. Charts are small client islands using Chart.js. Styling is plain CSS on the brand tokens (`brand/tokens/tokens.css`), no CSS framework.

**Tech Stack:** Astro 5, @astrojs/node, TypeScript, openapi-typescript + openapi-fetch, Chart.js, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-10-custom-golf-stats-v1-design.md` §3.4, §3.5, §4. Brand: `brand/BRAND.md` (binding for every visual decision). API: `src/CustomGolfStats.Api/Features/*` and the OpenAPI document.

## Global Constraints

- Brand is binding: colours only through the semantic CSS variables in `brand/tokens/tokens.css` (light and dark themes, `prefers-color-scheme`); fonts Space Grotesk (headings), Inter (body), JetBrains Mono with tabular figures (all numbers, stat labels uppercase 12px 0.08em); logos from `brand/logo/svg` (dark header uses `lockup-horizontal-on-dark.svg`); favicons/manifest/OG from `brand/web` copied into `web/public`; cards are white surface + 1px border, no shadows/gradients; one accent per region; Pin Orange text never on light (use `accentText`); signed numbers always show the sign with a real minus (U+2212). Content max width 1200px, 24px page padding, nav wraps on phones. Never invent colours or logos.
- Server-only API access: the browser never sees a token or talks to the API directly. `API_BASE_URL`, `SESSION_SECRET` from environment; never committed.
- Every protected page is protected by middleware; admin pages additionally require `role === 'Admin'` from `/me/entitlements` (the API enforces it too; hiding is never the only protection).
- Forms are plain HTML forms posted to Astro endpoints (progressive enhancement); API validation problems (400 `errors` keyed by field) are shown next to the fields; 409/502 problem details are shown as a message.
- Accessibility: semantic HTML, labelled inputs, 44px targets, visible focus, tables with `<th scope>`, charts have a data table fallback.
- Numbers formatting in one module: percentages to 1 dp, averages to 2 dp, to-par as `E`/`+n`/`−n`, `null` values as `–`.
- Tests: Vitest for modules (session crypto, formatting, API error mapping, route guards); Playwright end-to-end against a **fake API** (`web/tests/fake-api.ts`, a small Node HTTP server returning fixture JSON shaped by the OpenAPI types) started by Playwright's `webServer`, so e2e needs no .NET or database. `npm run check` (astro check + tsc), `npm test`, `npm run e2e` all pass with zero warnings/errors.
- CI: add a `web` job to `.github/workflows/ci.yml` (Node 24, `npm ci`, check, unit, e2e with Playwright Chromium).

## Review Focus

1. **No token reaches the browser** (no token in HTML, JS, URLs or non-httpOnly cookies); tampered/expired cookies are rejected and cleared; refresh works; sign-out clears the cookie. Tests in Task 1.
2. **Every protected route redirects when signed out; every admin route 403s for a non-admin** — enumerate the pages in a test rather than listing them by hand. Tests in Tasks 1 and 4.
3. **Stats pages show exactly the API's numbers** with consistent formatting and nulls as `–`; empty years render without errors. Tests in Task 2.
4. **Brand fidelity** in both themes (screenshots in the report for the main pages, light and dark).

### Task 1: Skeleton, brand, API client, session and auth pages
- Scaffold `web/` (Astro 5 + Node adapter, strict TS), copy brand assets, global styles from tokens, both layouts (dark header with the horizontal lockup, nav: Stats, Rounds, Courses, Profile, Admin for admins; footer), theme follows the OS.
- `gen:api` script and committed `schema.d.ts`; server client with problem-details mapping.
- Session cookie (AES-256-GCM, versioned, expiry), middleware (guard, refresh ~1 min before expiry, clear on failure), sign-in, sign-up (register then log in), sign-out, a landing page with the tagline.
- Fake API server and Playwright config; Vitest config.
- Tests: session round trip, tamper → rejected, expiry/refresh, guard redirects for every page under `src/pages` except public ones (enumerate files), sign-in error display, no token in rendered HTML.

### Task 2: Stats and scorecards (parallel after Task 1)
- Year picker from `/stats/years`, default the latest year. Overall: tiles (handicap index, 18-hole average, holes played, +/- par) and charts (driving accuracy, GIR, scoring percentages, recovery, putting averages, handicap history) — use the section endpoints' numbers. Season (counts, histograms 9 and 18 as bar charts), Season results table (link to scorecard), Career table, Scoring, Off the tee, Approach and around the green, Putting, Courses table, Handicap table + chart. Section navigation as tabs.
- `rounds/index` (list with year filter) and `rounds/[id]` scorecard (rows in API order: played holes in play order, then unplayed; front/back/total subtotals only when holes 1–9/10–18 are all played once).
- Tests: each page renders fixture numbers through `format.ts`; empty year; scorecard with a hole played twice; chart fallback table present.

### Task 3: Courses, profile and handicap (parallel after Task 1)
- Course search (our DB) with a "search the course database" step (`/courses/provider-search`, import button, "already imported" link), course detail (tees, current version, holes, versions history, flag form), manual course entry (tees with holes; client-generated ids for idempotent retry), edit details, new tee version, add tee; Verified-course edits show "sent for review" on 202.
- Profile edit (full-replace semantics: the form always sends every field), handicap history list/add/delete.
- Tests: search → import flow, manual create validation errors keyed by field, 202 message, profile save, handicap add/delete.

### Task 4: Admin (parallel after Task 1)
- Admin dashboard (open flags count, courses by status), users (search, set tier/role/disabled; can't demote yourself — show the API's error), courses (filter by status, edit, verify, correct a version in place with the "this changes played rounds" warning, merge with target picker and the 409 unmatched list), flags queue (resolve/dismiss), settings (trial rounds).
- Tests: non-admin gets 403 page on every admin route (enumerated), each action posts the right API call and shows the result.

### Task 5: CI and final review
- `web` CI job; README section in `web/README.md` (env vars, scripts, how to run against a local API).
- Whole-branch review, fixes, roadmap update.
